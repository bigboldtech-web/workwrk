### Access

Vocabulary is the access model's and nothing else: org roles Owner, Admin, Member, Guest plus the Agent flag and the People team; object roles Full access, Can edit, Can comment, Can view.

- **Table** is `GrantObject.TABLE` (access §3.2). A table anchored to a Space inherits the Space and its own grants add; a standalone table is creator Full access, plus the migration's "Everyone at {org} · Can edit" row for rows that are org-wide today (access §3.3). This replaces the situation the audit found (data.md §5: no per-table roles, no view-only share, no lock, no owner shown) and it replaces the `visibleSpaceIds` read gate plus the "read implies write" decision in `docs/plans/tables.md` §3a: read no longer implies write, because Can view now exists as a real, renderable role and the migration writes Can edit for everything that can write today, so nobody loses an ability on the day it ships.
- **The role select on a table offers all four roles**, because access §6.1 defines one role select ("Can view, Can comment, Can edit, Full access with the four blurbs") with no per-object-type variant, and the one share dialog belongs to the access unit. A Can comment holder on a table therefore gets exactly what Can view gets, which is honest: nothing on a table accepts a comment today, so the level grants no extra ability and takes none away.
  **Change request T-A1 to the access unit** (the same shape the docs unit raised as A3 for a canvas, `spec-docs-knowledge.md` §2 `/canvas/[id]`): drop **Can comment** from the role select for `{ type: "table" }`, on the rule that a level which does nothing must not be grantable. If the access unit accepts it, the table's select reads Full access · Can edit · Can view, and a COMMENT grant inherited from a Space still renders as "Can comment" in the People with access list, so the vocabulary never changes and no stored grant is rewritten. Until it accepts it, **the four-role select ships**. This spec does not change the dialog on its own.
- **Form** is anchored, not free-floating, and the anchor rule is access §3.3's: "Form: anchored to a Table (Tables module, rule 2); **inherits the Table; creator FULL**; responding = COMMENT for anyone the form is shared with, or the public-link rule under toggle 10." Two things follow and neither is negotiable here. First, **the creator keeps Full access for the life of the form**, whatever it is anchored to and whoever else holds what; the person who built a form can always edit, share, export and delete it, and choosing a destination can never take that away. Second, a form has no `GrantObject` of its own: it is never shared directly, and its Share dialog opens on its anchor with the header line "Access to {form} comes from {anchor}", the pattern the docs unit uses for a file (`spec-docs-knowledge.md` change request A1).
  **Change request T2 to the access unit.** Access §3.3 names a **Table** anchor only, because that is the module the Form lived in when the line was written; in the product a form's destination is usually a **List** (`board-form-view.tsx`, `createBoardItem`), and `settings-architecture.md` §7.1a says "object ladder on the List the form feeds". The extension this unit needs, in the access spec's own vocabulary, is one clause: *"Form: anchored to the Table or the List it feeds; inherits the anchor; creator FULL; a form with no destination yet inherits nothing and is creator FULL plus Admin FULL until one is set."* This spec builds that clause and flags it rather than asserting it, because access wins on access. Nothing else about the form changes: the builder still states the consequence plainly under the destination picker ("Editors of Sales · Q4 leads can edit this form and read its responses"), and because the creator keeps Full access, pointing a form at a List you only hold Can comment on costs you nothing.
- **Responding** needs Can comment or above on the anchor (access §3.1: Can comment grants "respond to Forms"), or the public link under the rule below.
- **Public links** on a table or a form are one row in the share dialog, governed by the org setting the access spec keeps on `/settings/access` › Guests and links (toggle 10). It has exactly **two values, Off and View only, default Off** (access §8 toggle 10, rendered as exactly those two by `settings-architecture.md` §5.7 card 3), and access §11 invariant 19 makes "public links are off by default and **never exceed VIEW**" a golden-tested security invariant. This spec invents no third value. What each value does here: **Off**, the public-link row is absent on every object for everyone, `/forms/[id]/respond` and both `/embed/*` routes serve the neutral invalid-link card, and the `isPublic` columns are ignored on read. **View only**, a table may publish a read-only grid and a form may publish a responder that anyone with the link can **open and fill**, with **Submit requiring sign-in** (the visitor is sent to `/login?callbackUrl=` with their typed answers preserved, §2). Turning a public link on requires **Full access** on the object and a confirm naming what becomes visible, and it writes an audit row, which replaces the one-click un-confirmed `isPublic` PATCH any member could send (data.md 3.9).
- **Open question for the founder, genuine: may a stranger without an account submit a form?** Today's product intends yes (`FormDefinition.isPublic` is documented as "anyone with the link can submit, no login needed" and `POST /api/forms/[id]/submissions` already honours it for anonymous writes), and a form that cannot take an answer from a customer, a candidate or a supplier is not a form. The decided access model does not allow it: an anonymous submission is a write, toggle 10 has no value that carries one, and invariant 19 forbids a public link from exceeding VIEW. This is the one place where the headline fix in data.md 3.3 and critic issue 8 needs a decision rather than a design, so it is stated instead of quietly invented. **What ships either way:** the responder leaves `(dashboard)`, so anyone with the link **reaches and reads** the form instead of bouncing to `/login`, which is the larger half of 3.3 and needs no new access value. **What the answer changes:** whether Submit asks a stranger to sign in first. Recommendation if the founder says yes: the access unit adds **one named exception**, not a third value on toggle 10, so invariant 19 keeps its meaning for every other object. Its shape, written so it can be pasted: a per-form switch **"Accept responses from people without an account"** (default off, Full access to turn on, confirm, audit row), rendered only when the org's public links are set to View only, granting exactly one capability, `respond` on that one form, and never `view` on the anchor, the destination List or any row already in it. Anything wider than that single append is a No, and it is **never a third value on toggle 10**, so invariant 19 keeps its meaning for every other object in the product.
  **Cross-unit resolution (access-model-spec, tables-forms, existing-direction), paired with the Forms-Core question in §1 Module off.** Build the access spec's version and put the question to the founder. **The larger half ships now and needs no answer**: the responder leaves `(dashboard)` for `(public)`, so anyone with the link reaches and reads the form instead of bouncing to `/login`, and **Submit requires sign-in with typed answers preserved** across the round trip. Only the Submit branch waits on the founder.
- **Agents** (the Member flag) never see Move to Trash, Delete table, Delete form, Delete responses, or any Export or Download row (`cap.agent.delete`, `cap.agent.export`). Everything else is a Member's.
- **Guests** reach `/tables/[id]` or `/forms/[id]` only through a direct share on the object or its anchor, and then only at the granted role. Guests never see the hub's create menu and never see Trash. A Guest **with at least one shared object** sees `/tables` or `/forms` as a list of exactly those rows. A Guest **with nothing shared in this hub** has no `tables` app row at all, which is access §5.2.1's Guest column, so `/tables` and `/forms` are the **shell 404** (access §5.5 items 2 and 6), never an empty list and never `<AppOff>`: an empty list would confirm the hub exists for them, and the app-off screen names an app they are not entitled to know about.
- **Read-only viewers** (access §5.4): a Can view viewer on a table sees the grid, the menu bar with only view-safe rows (View, and File › Download and Print unless they are an Agent, and Edit › Copy and Find), the formula bar showing the source of the selected cell and refusing input, the Filter chip and Sort, the status bar, Copy link, and a "Can view" chip where Share stands. Not rendered: every format control in the toolbar, the "+" column and row affordances, the column and row menus' mutating rows, cell editing, paste, the fill handle. Cells show a lock cursor on hover. One slim banner under the header: "View only. Ask {owner} for edit access." with a Request text link. **A Can view or Can comment viewer on a form** sees the Build tab as a read-only preview, the Settings tab as read-only cards, and no Responses tab at all (absent, not empty), because reading other people's answers is an editor's right. The two differ in one line: a Can comment holder, who may answer the form, also gets a 13/500 `--os-brand-deep` text link "Open the form to answer it" under the banner, pointing at `/forms/[id]/respond`. Neither role is ever redirected anywhere (§5.5 keeps `/login?callbackUrl=` as the only redirect in the system).
- **Denial**, one convention (access §5.5): not signed in on a shell route → `/login?callbackUrl=`; signed in and not discoverable → the shell 404 (tables and forms are never findable, so an id the viewer holds nothing on is a 404, never a locked page, and never a name); discoverable only as a container label → `LockedPage` with Request access; holds a role but not the action → the control is not rendered, and a stale-tab call returns 403 and raises one toast "You need Can edit for that. Ask {owner}." with Request access; module off → `<ModuleOff>`; app hidden or floored in Settings › Apps & modules → `<AppOff>`.
  **The three denial shapes, settled once across every unit so nobody applies the wrong one.** They are three different situations, not three opinions about one situation:
  1. **An app key the viewer's rule excludes** (access §5.2.1 rule 6, no object loaded, so there is nobody to request from) → the **in-shell 404**, and **no sidebar row** for it. This is the Guest with nothing shared in this hub: `/tables` and `/forms` are the shell 404, never an empty list.
  2. **A view of a page the viewer already holds** (the shape `/planner?calendar=team` and `/timesheets?view=approvals` take elsewhere; here `?view=` on `/tables` and `/forms` and `?tab=responses` on `/forms/[id]`) → render the **default view**, strip the parameter with `router.replace`, and show **one 13/400 notice line** (access rule 4). Never a locked page and never a 404: the page is the viewer's, only that slice is not. This is why the Responses pill is absent for a Can view holder and `?tab=responses` lands them on Build with the notice line rather than on a denial screen.
  3. **An object the viewer can discover but holds no role on** (access rule 3) → **`LockedPage` with Request access**. For this unit that is a table discoverable through a Space the viewer can see.
  `<AppOff>` is **only** for an app the org hid or floored in Settings › Apps & modules, and `<ModuleOff>` is **only** for a premium module switched off. Neither is ever used for a rule-excluded app key, a stripped view parameter or a missing object role. The public routes resolve in one order, and it is the order that keeps an internal form answerable while a public one stays anonymous-safe. `/forms/[id]/respond` and both `/embed/*` routes ask two questions, public first: **(1) is the object's public link on and does the org's toggle 10 allow it?** If yes, the page renders for anyone, signed in or not. If no, **(2) is there a session, and does that person hold Can comment or above on the form's anchor?** If yes, the page renders for them, which is how an internal form reaches the colleagues meant to answer it. Only when both answers are no does the page render the neutral **"This link is invalid or has been turned off."** with no object name, no org name and no difference between "wrong id", "not public" and "not shared with you". A signed-out visitor is never redirected from these routes: the invalid-link card carries one 13/500 text link "Sign in to WorkwrK" (`/login?callbackUrl=`), so a colleague who simply is not signed in has a way through and a stranger learns nothing.

- **Who sees it and entry points.** The form's **creator always** (creator Full access, access §3.3, and it never lapses), plus anyone holding Can edit or Full access on the form's anchor, plus Owners and Admins. **Can view and Can comment holders get the read-only builder** described under States, at this URL: neither is redirected anywhere, because access §5.5 keeps `/login?callbackUrl=` as the only redirect in the system and item 4 says a role that lacks an action simply does not see that action's controls. A Can comment holder, who may answer the form, gets one text link "Open the form to answer it" under the view-only banner; nothing bounces them there. Entry: `/forms` rows, the Tables sidebar FORMS rows, the board FORM view's "Edit form" (`board-form-view.tsx:178-184`), the doc `form` block "Open", the Activity feed, the global "+" menu "Form", the RELATIONSHIP field entity picker (`field-value.tsx:1105`), the AI tool `create_form`, and `?new=1` from any create door.
- **Top bar.** Left: ‹ › then **Tables › Forms › {Form name}**. Centre: search. Right: the shell cluster.
- **Secondary sidebar.** Tables hub sidebar; the form's FORMS row active when it is listed, otherwise "All forms".
- **Page header stack.**
  - Title row 48: `BackButton{fallbackHref}` (the destination, else `/forms`), `EntityTile size="lg"` neutral with `ClipboardList`, the **name** as an inline-editable 22/600 field (placeholder "Untitled form"), the `AutosaveIndicator`, the `Star`. Right, in order: the real avatar stack (the anchor's grants, since a form has no grants of its own), the `Globe` or `Lock` glyph, **`ShareOrRoleChip`** (ghost `Share2` + "Share", or the role chip; design §4.4 "ghost page actions only", the same control as every other object page), the bordered "…" (the `/forms` row menu minus Open), then the "Ask AI" slot when entitled. The dialog it opens is the one share dialog on the **anchor**, headed "Access to {form} comes from {anchor}".
  - Views row 36: text-tab pills **Build · Settings · Responses**, mapped to `?tab=`. The Responses pill carries the live count at 12/500 (today the count comes from the initial GET and never refreshes, data.md 2.4). The Responses pill is absent for a Can view holder.
  - Toolbar 44: left **Preview** (36px secondary button, `Eye`, opens the preview drawer) and, on the Responses tab only, **Filter** and **Sort**. Right: **Copy link** (36px secondary, `Link2`) fused to a split chevron (Copy embed code, only when a public link is on), then the bordered "…": on Build, Display (Show help text, Show field numbers); on Responses, Export as CSV (absent for Agents) and Delete responses (Full access, typed confirm). **No blue button on this route either**, for the same reason as the sheet: the builder creates nothing, Share is the title row's ghost, and design §4.4 keeps the toolbar's one blue button for create actions.
- **Body layout.**

  **Build tab.** One 720px column, centred, 24px page padding.
  1. **Form header card** (`--os-line` border, radius 8, padding 24): the form's **Title** (a 16/600 input, defaults to the form name and stays in sync until edited) and **Description** (a 3-row auto-growing textarea, max 12, 14/400). The API has accepted `description` all along and AI-generated forms fill it; the builder never showed it (data.md 3.18, 2.4).
  2. **Field cards**, one per field, in order. Each card: a `grip` drag handle (design §5.16) on the left edge, visible on hover and on focus; the **type chip** (a neutral `Chip` at 12/500 with the type glyph); the **Label** input (14/400, placeholder "Question"); the **Help text** input (13/400 `--os-ink-2`, placeholder "Optional", writing the `placeholder` field the type already has); for Single choice and Multiple choice an **Options** editor (one option per row at 36px, drag to reorder, a ✕ per row, a "+ Add option" ghost row, and an "Other" switch) replacing the raw "one per line" textarea; a **Required** switch (the shared `ui/switch`, not a native checkbox); and a "…" menu: **Duplicate · Move up · Move down · Change type ▸ · Delete**. Changing the type is possible for the first time (data.md 2.4) and warns when options or answers would be lost.
  3. **"+ Add a field"** ghost row at the bottom of the column, full width, 36px, which opens the `Picker` (280) listing the nine built types in this order: **Short text · Long text · Number · Email · Link · Date · Single choice · Multiple choice · Checkbox**. The right-hand 240px aside of nine buttons goes; a `Picker` is what the rest of the product uses and it survives narrow widths. No unbuilt type is listed; file upload, rating, signature and the rest live only under the "Show upcoming features" preference as a single "More field types are coming" line, never as disabled rows.
  4. **Goes to card**: a `Picker` trigger, "Goes to", with two groups, **Lists** (from `GET /api/lists`, the canonical Board and Item model) and **Tables** (from `GET /api/tables`, absent when the module is off), plus "Nowhere yet". The legacy `/api/studio/boards` and `/api/studio/boards/[slug]` calls go, which closes the mismatch between the columns the mapping offered and the keys the submit handler writes through `createBoardItem` (data.md 3.12). Under the trigger, one 13/400 `--os-ink-2` line naming the resulting audience: "Editors of Sales · Q4 leads can edit this form and read its responses."
  5. **Field mapping card**, rendered only when a destination is set: a two-column grid, "Form field" on the left at 15/400 and a column `Picker` on the right, defaulting to "(match by name)". The table side now lists **column names**, which exist at last, so the blank options and the impossible auto-match are both fixed (data.md 2.4, 3.1). Unmapped fields show "Not sent" in `--os-ink-2` and a one-line note under the card: "Answers to unmapped fields are still saved and shown on the Responses tab."

  **Where every value on this tab lives**, because `settings-architecture.md` §9.1 is "if it renders, it persists, and something reads it" and §9.2 requires a storage class per value. Storage class: **object-scoped** (§9.2's last row: object APIs, object Full holders, never inside a settings door). Store: a **new `FormDefinition.settings` JSON column** (`schema.prisma` has `name`, `description`, `fields`, `isPublic`, `targetBoardId`, `targetTableId`, `fieldMappings` and no settings bucket, so this is one additive migration, §4). Writer: `PATCH /api/forms/[id] { settings }`, validated by one `.strict()` zod schema in `src/lib/forms/settings.ts` so an unknown key is a 400 that names it, never a silent strip. Readers: `GET /api/forms/[id]` (the builder) and `GET /api/public/forms/[id]` (the responder and the embed).

  - A row click opens the **response drawer** (520, at `?response=<id>`): every field and answer as 36px label and value rows, the destination link, the submitted time, the responder, and a destructive ghost "Delete response" for Full access holders.
  - Footer row 44 with "Total records N" and pagination; the server-side `take: 500` with no cursor is replaced by a real cursor (critic issue 12).
  - The `<details>` accordion rows go.

- **Side panel / drawer / modal.** **Preview drawer** 520, right, at `?preview=1`: the exact `FormRenderer` the responder and the embed use, in a disabled-submit state with a 13/400 banner "This is a preview. Nothing is saved." Share dialog 560. Change-type and destination confirms 400. Delete confirms 400 (typed confirmation for "Delete all responses").
- **States.**
  - Loading: rail pulse plus skeleton cards.
  - Empty (Build, no fields): the quiet template inside the column, four dots in a row, "No questions yet", one text link "Add a field". No button, because there is no primary on this route.
  - Empty (Responses): four dots in a row, "No responses yet", one text link "Copy the link to share".
  - Error: "We could not load this form." plus Retry.
  - Read-only: a Can view holder sees the Build tab as a rendered preview with no inputs, the Settings tab as label and value rows, no Responses tab, the "Can view" chip instead of Share, and the banner "View only. Ask {owner} for edit access."
  - Denied, the three shapes of §1 Access and nothing else: **404 in the shell** for an id whose anchor the viewer holds nothing on, and for a viewer the `forms` app rule excludes (no sidebar row either); **`LockedPage` with Request access** when the anchor is discoverable but the viewer holds no role on it; **`<AppOff>`** only when the org hid or floored the `forms` app in Settings › Apps & modules, and **`<ModuleOff>`** only when the spreadsheets module is off. A `?tab=responses` a Can view holder cannot use is not a denial at all: the page renders Build, `router.replace` strips the parameter, and one 13/400 notice line says why.
  - Offline or session expired: the shell bar; the builder stops autosaving, the indicator reads "Not saved", the typed text stays on screen, and the retry after sign-in replays the pending PATCH.
- **Keyboard.** `⌘S` is not bound (there is nothing to save). `Tab` and `⇧Tab` move between field cards; with a card's drag handle focused, `⌘↑` and `⌘↓` move the field; `.` opens the focused card's "…"; `⌘E` opens Preview; `Esc` closes the preview or the drawer; `1`, `2`, `3` switch tabs when focus is on the views row.
- **Data.** **One vocabulary, applied all the way down.** The naming canon pins **Response** over "Submission", so the whole route family is renamed in one change and there is never a moment when two paths serve the same rows: `/api/forms/[id]/submissions` **becomes** `/api/forms/[id]/responses`, and the old path stays mounted for one release as a 307 to the new one so nothing in the wild breaks (`formSubmission` stays the Prisma model name and is never shown to a person). After that release the old path is deleted with its tests.
  - Existing, unchanged: `GET /api/forms/[id]`, `PATCH /api/forms/[id]`, `DELETE /api/forms/[id]`, `POST /api/forms/generate`.
  - Renamed: `GET /api/forms/[id]/responses?cursor=&q=&sort=` (this is the one path the Responses tab reads; it replaces `GET …/submissions` and its `take: 500` with a real cursor, critic issue 12) and `POST /api/forms/[id]/responses` (the one submit path, used by the responder, the embed and the board FORM view; it replaces `POST …/submissions`).
  - New: `POST /api/forms/[id]/duplicate`; `GET /api/forms/[id]/responses/export.csv` (honours the active filter and sort; absent for Agents); `DELETE /api/forms/[id]/responses/[responseId]`; `DELETE /api/forms/[id]/responses` (delete all, typed confirm, Full access); `GET /api/lists?forForm=1` (the canonical replacement for `/api/studio/boards`).
  - Changed: `PATCH /api/forms/[id]` accepts `settings` (the strict schema above) and stops accepting `isPublic` directly, which now moves only through the share dialog's public-link write with Full access and an audit row; every `/api/forms*` handler moves from `getSessionOrFail` to `requireCan(action, anchorRef)` per §1 Access, with the creator's Full access resolved first so the person who built a form is never locked out of it. This ends today's situation where any org member could edit, retarget, publish or delete any form (data.md §5).
  - Settings it reads: `settings.access.publicLinks`, the module installation, the AI module entitlement, and the form's own `settings` bucket above.
- **Realtime.** The Responses tab refetches on window focus and every 30 seconds while it is the active tab, and the count on the Responses pill updates from the same fetch. Nothing else polls.
- **What changes vs today.**
  - Manual Save with no dirty state and no leave guard is replaced by autosave with the `AutosaveIndicator` contract, which is strictly safer than a guard (data.md 3.4, critic issue 7). `useDirtyGuard` is still mounted, armed only while a save is in flight or has failed, which satisfies `settings-architecture.md` §8.5 without reintroducing a Save button.
  - "Share link" now hands out a link that works for the person it is handed to (the responder moves to the public route group, below).
  - Field type can be changed, help text exists, options have a real editor, the form description exists, drag reorder exists next to the keyboard and menu paths (2.4).
  - Every missing form setting in data.md §6 that has a reader is built: confirmation message, redirect, accepting responses, close date, one response per person, collect email, notify on response. Everything with no reader is absent, not stubbed.
  - Public and Org-only stops being a native checkbox inside a label and stops being called two different things on two pages (2.4).
  - The board FORM view's "Copy link" copies the responder URL, not the chrome-less embed URL, so the person who receives it can open it (2.8); "Embed code" stays for iframes.
  - Responses gain a person, a destination link, a drawer, export, delete and paging.
- **Open questions.** None.

### /forms/[id]/respond  (moves to src/app/(public)/forms/[id]/respond/page.tsx)

- **Purpose.** Fill in a form and send it, whether or not you have a WorkwrK account.
- **Who sees it and entry points.** Two branches, resolved in the order §1 Access fixes, and they are the same two branches the Denied state below tests, so an engineer builds one rule and not two. **(1) The public link is on** (the object's link is on and the org's toggle 10 is View only): anyone with the link opens the page, signed in or not. **(2) The public link is off**: the page still opens for a signed-in person who holds **Can comment or above** on the form's anchor, which is how an internal form reaches the colleagues meant to answer it. Only when neither branch is satisfied does the page render the invalid-link card. Entry: the builder's Share (Copy link), the `/forms` row menu "Open the form", the doc `form` block "Click to fill this form", the AI tool's `responderUrl`, and any link a person pasted anywhere.
- **Top bar.** None. This route renders no shell (the `(public)` group, like `/(public)/share/doc/[token]`). The page has its own 56px bar: the WorkwrK four-dot mark plus wordmark at the left, and, for a signed-in visitor only, one 13/500 `--os-brand-deep` text link "Open in WorkwrK" at the right.
- **Secondary sidebar.** None.
- **Page header stack.** Not the list-page stack (this is not a list page). The form's own header sits inside the content card: the **title** at 22/600 `--os-ink` and the **description** at 15/400 `--os-ink-2` beneath it, then a 1px `--os-line` rule.
- **Body layout.** A 640px column centred on `--os-canvas`, 48px top padding, 24px inline padding, inside one bordered card (`--os-surface`, `1px solid var(--os-line)`, radius 8, padding 32). Fields in order, each a 16px-separated block: label at 14/500 `--os-ink` with "(required)" as plain text at 13/400 `--os-ink-2` after it (never a red asterisk, design §5.4); help text at 13/400 `--os-ink-2`; the input at 36px per design §5.4, or a 3-row auto-growing textarea for Long text, or 36px radio rows for Single choice, or 36px checkbox rows for Multiple choice, or one 36px switch row with the field's own label for Checkbox (today it is hard-coded "Yes", data.md 2.5), or the date `Picker` for Date. The number field stores `null` when cleared, not `""`. Footer: one blue **"Submit"** button (36px, the one primary on this page), left aligned under the last field, with the `pending` four-dot mini-loader replacing its icon while the POST is in flight.
- **Side panel / drawer / modal.** None. A public page has no drawers.
- **States.**
  - Loading: three skeleton field blocks inside the card. No rail pulse (there is no rail); no `ValueLoader` and no `Loader2`.
  - Empty (the form has no fields): "This form has no questions yet." at 15/400 `--os-ink-2`, centred, with no Submit button.
  - Error (network or 5xx): "We could not load this form." plus a wired Retry.
  - Validation: **inline**, never a modal confirm and never an `alert()` (data.md 3.16, 2.6). On Submit, every missing required field gets a `--os-danger-solid` border, a 13px `--os-danger-text` helper with a 16px `CircleAlert` ("Please answer this question"), and focus moves to the first one; a single 13/400 `--os-danger-text` line above the Submit button counts them ("2 questions need an answer").
  - Success: the card is replaced by the quiet template, the confirmation message from Settings at 15/400 `--os-ink`, and, when the setting is on, one text link "Submit another response". When a redirect URL is set the page navigates instead, after a 1s "Thanks, sending you on" line.
  - Closed: the closed message from Settings, centred, with no inputs and no Submit.
  - Denied (neither branch of "Who sees it" is satisfied: the public link is off **and** the visitor is signed out or holds nothing on the anchor; or the form is deleted; or the id is wrong): one line "This link is invalid or has been turned off.", plus one 13/500 text link "Sign in to WorkwrK" (`/login?callbackUrl=`) so a colleague who is simply signed out has a way through. No form name, no org name, no difference between the cases, and no automatic redirect.
  - Read-only: **not applicable in the usual sense** (a public page has no roles to render read-only), with one real case named so it is not discovered late: a form whose *Accepting responses* switch is off or whose close date has passed renders its **Closed** state below, which is this page's read-only, the fields visible and no Submit.
  - Offline or session expired: **while the decided access model stands, Submit requires a session** (§1 Access public links: View only carries reading, not writing). A visitor who reaches Submit without one is sent to `/login?callbackUrl=<this URL>` (the one redirect in the system) and comes back with every typed answer restored from `sessionStorage`; a signed-in responder whose session lapses mid-form gets a 401 on Submit and one bar "You have been signed out. Sign in to send this." with a Sign in link that does the same round trip. Answers are never lost to a session expiry or to a sign-in. If the founder answers the §1 anonymous-responses question with yes, one branch is added here and nothing else changes: a form with that switch on submits without a session and never shows the bar.
- **Keyboard.** `Tab` and `⇧Tab` between fields, arrows within radio and checkbox groups, `Enter` submits from any single-line input, `⌘Enter` submits from a textarea.
- **Data.** New: `GET /api/public/forms/[id]` returning `{ id, name, description, fields, settings: { acceptingResponses, closesAt, confirmationMessage, redirectUrl, allowAnother, requiresSignIn, collectEmail, closedMessage } }` and 404 for anything neither branch of "Who sees it" allows; this is the route the product never had (`api/public/` holds docs, run, sign and tables and no forms, data.md 3.3). It answers for both branches: no session and a live public link, or a session that `requireCan("respond", anchorRef)` clears. Submit: `POST /api/forms/[id]/responses` (the renamed path, §2 `/forms/[id]`), which enforces accepting-responses, the close date and the one-per-person rule server-side, and which requires a session under the decided model. `proxy.ts` and the edge auth gate add `/forms/*/respond` and `/api/public/forms/*` to the public allowlist. Settings it reads: `settings.access.publicLinks` and the form's own `settings` bucket.
- **Realtime.** None.
- **What changes vs today.** The page leaves `(dashboard)`, so a visitor with the link **reaches and reads** the form instead of being bounced to `/login` (data.md 3.3, critic issue 8); what a stranger may then do at the Submit button is the founder question below. It stops rendering inside the OS canvas with `.resp { min-height: 100vh; padding: 60px 24px }`, which produced a nested scroll and a 60px gap under the topbar (2.5). Validation stops being a modal confirm per missing field. The checkbox field uses its own label. The renderer is the one `FormRenderer` shared with the embed and the builder's preview, so the two copies of `FieldInput` become one (2.6, critic issue 14). A signed-in colleague can answer an internal form that has no public link at all, which the old page allowed by accident and the new rule allows on purpose.
- **Open questions.** One, and it is §1 Access's: **may a stranger without an account submit?** The decided access model says no (toggle 10 has two values, and invariant 19 keeps a public link at Can view), so this page ships with Submit requiring sign-in and every typed answer preserved across it. §1 carries the full question and the one-switch shape the access unit would need if the answer is yes; it is repeated here only because this is the page where a founder will notice it.

### /embed/forms/[id]  (src/app/embed/forms/[id]/page.tsx)

- **Purpose.** The same form, with no chrome, inside somebody else's page or inside a List's Form view.
- **Who sees it and entry points.** Anyone the iframe reaches, under the same rules as the responder. Entry: the builder's "Copy embed code", the `/forms` row menu "Copy embed code", and the board FORM view's iframe (`board-form-view.tsx:198`).
- **Top bar.** None, and no WorkwrK bar either: an embed shows one thing. A 12/400 `--os-ink-3` "Powered by WorkwrK" line sits under the card, linking to the marketing site with `rel="noopener"`, and it is the only branding.
- **Secondary sidebar.** None.
- **Page header stack.** The form title and description inside the card, as the responder.
- **Body layout.** The same `FormRenderer` at a fluid width with a 640px max, 16px padding, `--os-canvas` background, no outer card border below 480px (the host page provides the frame). The iframe snippet the product copies is `<iframe src="{origin}/embed/forms/{id}" width="100%" height="640" style="border:0" title="{form name}"></iframe>` and it is shown in a copyable code block in the builder's Copy link split menu, not pushed straight to the clipboard with a toast that warns you to go turn Public on afterwards (data.md 2.4).
- **Side panel / drawer / modal.** None.
- **States.** All six, written out, because "identical to the responder" does not transfer cleanly into an iframe on somebody else's page: an embed cannot navigate the host, cannot open `/login` inside itself without trapping the visitor, and has no chrome to hang a bar on.
  - **Loading:** three skeleton field blocks inside the card. No rail pulse, no `Loader2`, no inline `@keyframes`.
  - **Empty** (the form has no fields): "This form has no questions yet." at 15/400 `--os-ink-2`, centred, no Submit.
  - **Error** (network or 5xx): "We could not load this form." plus a wired Retry that refetches inside the frame.
  - **Read-only:** the form is **Closed** (Accepting responses off, or the close date has passed). The fields render, disabled, under the closed message from Settings, with no Submit. This is the embed's read-only and it is the only one it has: an embed has no roles.
  - **Denied** (the public link is off, the org's toggle 10 is Off, the module is off, the form is deleted, or the id is wrong): the same one line, "This link is invalid or has been turned off.", with no form name, no org name and no module name. An embed never falls back to a sign-in prompt, because a host page cannot be asked to carry someone else's login; the second branch of the responder's rule does not apply here.
  - **Offline or session expired:** the frame never shows the app's offline bar. A failed load is the Error state above. A failed **Submit** is an inline 13/400 `--os-danger-text` line above the button with a **Retry** text link, never `alert()` (data.md 2.6), and the typed answers stay in the fields. When Submit returns 401 because a signed-in visitor's session lapsed, the line reads "You have been signed out. Open this form in a new tab to send it." with a text link that opens `/forms/[id]/respond` with `target="_blank"` and `rel="noopener"`, carrying the answers through `sessionStorage`. The iframe is never navigated to `/login` in place.
  - Validation is inline, exactly as the responder. The "Submit another response" link appears only when that setting is on, and "Open in WorkwrK" never appears here.
- **Keyboard.** As the responder. The iframe is focusable and the first field takes focus only on user interaction, never on load (an embed must not steal the host page's scroll).
- **Data.** `GET /api/public/forms/[id]` (new, above) and `POST /api/forms/[id]/responses` (the renamed submit path). The session-gated `GET /api/forms/[id]` is no longer called from here, which is the actual bug: an anonymous visitor got "Couldn't load this form: HTTP 401" even with `isPublic = true` (data.md 2.6, 3.3).
- **Realtime.** None.
- **What changes vs today.** It **loads** for anonymous visitors instead of returning "Couldn't load this form: HTTP 401", which is the bug (whether an anonymous visitor may then submit is the §1 founder question, and it is the same answer here as on the responder). The hard-coded palette goes: the `#5559DF` to `#A25DDC` purple gradient icon and the `#1f2937` charcoal button are replaced by `--os-*` tokens and the one blue primary, which also ends the palette violation the audit flagged (2.6, brand rule "no purple"). The duplicated `FieldInput` is deleted in favour of `FormRenderer`. The embed inherits the viewer's `prefers-color-scheme` through the same token rebinding as the app, so a dark host page gets a dark form.
- **Open questions.** None.
