# Task detail spec (drawer + full page, comments thread, create-task modal, pickers)

Unit key: `task-detail`. Date: 2026-09-11. Written against `design-system.md` (look), `access-model-spec.md` (access), `settings-architecture.md` (settings), the audit inventories `work-tasks.md` and `spaces-boards.md`, and the code at commit `6187227a`. Every path is repo-relative unless it starts with `/private/tmp`. Vocabulary: a "task" is an `Item` row; "List" is a `Board` row; the four object roles are Full access, Can edit, Can comment, Can view; the four org roles are Owner, Admin, Member, Guest.

One sentence: **one task body (`BoardItemDetail`), shown in one 520px drawer beside whatever list you came from or as one full page at the same URL, with four fields visible, a named "+ Add field" door, and one comment thread that can grow.**

## 1. Unit-level rules

### Hub + sidebar

- Every route in this unit sits in the **Work** hub. The active rail pill is Work whether the task is reached from a List, from My work, from search or from a notification. Planner and Goals surfaces that mount the `@drawer` slot keep their own hub while the drawer is open (the URL is `/item/[id]`, but the shell resolves the hub from the drawer's host surface, see the resolution rule below).
- Active secondary-sidebar row, URL-derived (never sticky): the task's **List row** in the Spaces tree, with its Space and Folder expanded; for a Personal List task the **My work › Personal list** row; for a Guest the shared List row in their scoped tree. The shell's URL-to-row resolver (shell unit) cannot read a task id, so the task page and the drawer call `useShellLocation({ hub: "home", listId, spaceId, folderId })` (shell unit's hook) as soon as `GET /api/items/[id]` returns; until then the sidebar keeps the row of the surface underneath (drawer) or shows no active row (hard load), never a stale hub.
- When the drawer is open over a host surface, the host's own active row stays active (it is the same List).

### Access

The task has no grants of its own (access spec §3.2). `can(viewer, action, { type: "item", id })` resolves as: rule 4 Owner and Admin FULL; rule 5 creator FULL; rule 9 assignee EDIT (plus VIEW-for-context on the List: its name, statuses and fields); rule 10 inheritance; rule 12 caps (Guest at most Can edit, Agent never `delete`, archived at most Can view unless FULL).

Rule 10 in full, because the short version is easy to get backwards: rule 10 applies rules 5 to 9 **to the parent List**, then walks upward to the Folder and Space, and a Restricted object **stops the walk at itself, not before itself**. So on a Restricted List, rules 5 to 9 still run on that List and everyone holding a direct grant on it (plus its owner and org Owners and Admins) keeps that role on every task inside; what stops is the Space's and Folder's grants reaching in. This is access example E read from the child's side, and it is the whole point of a private List: the people on it work in it. A task whose List is Restricted and whose viewer holds nothing on that List, nothing on the task and no assignment resolves to no role, which is the 404 case below.

Denial, one convention (access §5.5), and there are only three cases on a task:

1. **Not signed in** → `/login?callbackUrl=/item/<id>`.
2. **Signed in, no role on the task** → the shell's 404 inside the frame. There is no fourth case, because **a task is never discoverable**: access rule 14 grants discoverability only to a findable Space or public channel, to a container the viewer holds a role *inside*, or to the List that holds a task assigned to the viewer. An `Item` has no `findable` flag, no descendants a person can be granted on, and is not a container, so "role none" and "not discoverable" are the same state for a task. This matches access example J, where a Restricted List the viewer holds nothing in is a plain 404 rather than a locked page. **This spec therefore builds no task-level LockedPage, no task-level "Request access" primary and no back target on one.** A person who needs access asks for it at the object that can be requested: the List or the Space, reached from search or from the person who sent them the link. Raised as open question 6 to the access spec (§2 shared list) in case an item-level branch is wanted later; until it is answered, 404.
3. **Role below Can edit** → not a denial: the read-only rendering in the table above, with the one slim banner under the header ("View only. Ask {List owner} for edit access." with Request access, access §5.4) and a lock cursor on values. A control the role cannot use is not rendered, never disabled.

The drawer never renders a denial: a row the viewer cannot open never appears in a list they can read, so the intercept always has a role. If a stale tab loses access, the drawer body swaps to the same words the 404 page uses, "This task was deleted or you no longer have access", with one text link "Close" and nothing else, and the host list refetches behind it.

API enforcement: `GET /api/items/[id]` → `requireCan("view", { type: "item", id })`; `PATCH` → `requireCan("edit", …)` (this fixes today's mismatch where `GET` grants assignees `canEdit: true` at `route.ts:30-31` but `PATCH`'s `loadAndGate` at `:119-134` has no assignee branch and 403s them); `DELETE` (archive) → `edit`; `DELETE ?hard=1` → `delete` (the §9 `tasks.delete` rule: creator with Can edit, or Full access; Agents never); `POST /api/items/[id]/updates` → `comment`. Today the updates and activity routes resolve a Space first (`updates/route.ts:31-38`: `!item.board.spaceId` or `!getSpaceForReader(...)` → 404), which breaks two whole populations: an assignee in a Space they are not in gets a 404 thread, and **every Personal List task gets a 404 thread**, because the personal board has no `spaceId` at all. Both routes move to the item ref, which fixes both in one change. `requireCan` returns 404 (not 403) whenever the resolved role is none, per case 2 above; the 403 body `{ error: "no_access", reason, requestAccess }` is reserved for the role-too-low case (a stale tab writing to a task it may still read), and the client shows one toast "You need Can edit for that. Ask {owner}." with Request access pointing at the List.

### Mobile / narrow

- Under 1024px the drawer becomes a full-width sheet under the top bar (no resize handle, no list dim); the header keeps ✕ and Copy link; Expand is hidden (the sheet is already full width).
- Under 768px the field-strip label column shrinks from 120 to 96px; the title row wraps; the "…" menu holds Share and Ask AI; the comment composer is sticky above the bottom edge.
- The create-task modal is a full-screen sheet under 720px; the field chip row wraps to two lines; the primary stays in a 64px sticky footer.
- Pickers keep 280px and clamp to the viewport (`Picker` handles it).
- Drag (attachments drop zone, subtask reorder) has a keyboard and menu alternative: "Upload file" button, "Move up / Move down" in the subtask row menu.

## 2. Route specs

### `/item/[id]` (`src/app/(dashboard)/item/[id]/page.tsx`, full page)

- **Purpose**: open one task on its own page: read everything about it, change it, and talk about it.
- **Who sees it**: anyone with Can view or better on the task (see §1 Access); Guests for tasks on Lists shared with them; assignee-only Members. **Entry points**: hard load or new tab of the URL; Copy link; the drawer's Expand (in place, no navigation); global search result "Task"; command palette; Inbox rows for `task_assigned`, `task_status_changed`, `task_due_today`, `task_overdue`, `mention`, `task_comment` (all link `/item/<id>`, comments and mentions with `?comment=<updateId>`); the Reminders bell row for a task reminder; Planner task chips when the host does not mount the `@drawer` slot; a Doc, SOP or Canvas link to a task; a Goal's linked-task list; Talk message links; the Inbox pane's Expand (`/item/<id>?returnTo=/inbox?tab=…`, work-home unit). Not an entry point: `/trash`. The spaces-lists unit owns that page and its rows are not links (deleted and archived objects are reached by Restore, not by opening), so an archived task is opened only from its own link, where it renders read-only with the Archived banner.
- **Top bar**: left ‹ › then the hierarchy breadcrumb **Work › {Space} › {Folder} › {List} › {Task title}** (Space crumb with `EntityTile size="xs"`; each crumb a link where the viewer has Can view on that object, else a grey label; the last crumb 14/500 not clickable; middle crumbs collapse past 4 levels; Personal List task: Work › My work › Personal list › {Task}); centre: global search; right: "+", bell, help, avatar. Nothing task-specific goes on the bar.
- **Secondary sidebar**: Work hub; the task's List row active with its ancestors expanded (via `useShellLocation`); no row active for an assignee-only viewer.
- **Page header stack**: the doc-page variant (design system §4.4: title 48, no views row, no toolbar; chrome above content = 96).
  - **The title is rendered once, in the body, in both hosts.** The task name is an editable value, not page chrome, and one body means one title editor. So the 48px title row holds no editable title and the body's item 1 is the only place the name can be typed. This is the whole answer to "does the page render one title or two": one, in the body, in the 760 column, with the Type chip beside it, exactly as the drawer does.
  - **Title row (48px)**, left to right: `BackButton{fallbackHref}` (28px ghost, `ArrowLeft`, label per §1 Back / close) · a **condensed title label**, empty at scroll 0 and fading in (200ms `--os-ease-out`) at 15/500 `--os-ink` with a 320px ellipsis once the body title has scrolled out of view, so a long task still has a name on screen while you read the comments; it is never clickable and never editable · spacer · right cluster: `AutosaveIndicator`, a **role chip** for Can view / Can comment ("Can view" 24px neutral Chip, click opens the one share dialog in "Who has access" mode for the List; absent on a Personal List task), the **Watch** toggle (32px ghost icon `Eye` / `EyeOff`, tooltip "Watch this task · you get comments and status changes"), **Copy link** (32px ghost `Link2`), **"…"** (32px ghost `MoreHorizontal`), and the one **Ask AI** slot (28px ghost `Sparkles` "Ask AI") at the far right, rendered only when the AI module is entitled, calling the handler named in §0 (`useAiSession().start({ context })` then `openAskAi()`). No solid button on this page: the page's one blue thing is reserved for links, focus and checked controls. No star.
  - The **Type chip** is not header chrome either: it sits in the body beside the title (item 1), where it is the same control in both hosts.
- **Body layout** (760px max column centred, 24px padding, 32px between sections, the same `BoardItemDetail` the drawer renders, in this order):

For a reader below Can edit it is plain text with a lock cursor, not a disabled input. `PATCH { title }`. A draft title survives session expiry (see States, offline / session expired).
  2. **Field strip**: 36px `label / value` rows, label 13/500 `--os-ink-2` in a 120px column with a 16px Lucide glyph, value = a picker trigger that reads like text (hover `--os-surface-hov` radius 6). **Visible by default: Status, Assignees, Due date, Priority.** Then the **"+ Add field"** ghost row (15/400 `--os-ink-2`, `Plus`) which opens a `Picker` (280) listing every hidden field with a check: Start date, Estimate, Time tracked (only when the Space's Time tracking module is on), Tags (Tags module on), KRA / KPI, Watchers, then a section "List fields" with every custom field of the List (Custom fields module on), and a footer "Manage fields" (Full access only) that opens the List's Fields panel (`/boards/<slug>?panel=fields`, spaces-lists unit). The old solid pill, "›" advance segment and `onMouseLeave` close go. `PATCH { status }`.

     - **Watchers**: avatar stack; `Picker` multi over the same people source as Assignees; "Watch" / "Unwatch" for self. **Two lists, not one**, because one list cannot express "stop telling me": `Item.metadata.watchers: string[]` (people who are watching) and `Item.metadata.unwatchers: string[]` (people who have explicitly stopped). Today's `metadata.followers` is read as `watchers` and written back under the new name; `unwatchers` starts empty. The rules, in this order, on the server:
       - auto-watch on acting: creator, every assignee, every commenter and every mentioned person is added to `watchers` when they act, **unless their id is in `unwatchers`**, in which case nothing happens;
       - Unwatch (the header toggle, the "…" row, or removing yourself in the picker) removes you from `watchers` **and** adds you to `unwatchers`, so commenting again does not silently re-subscribe you. That is what makes "removing yourself sticks" true;
       - Watch (the same controls the other way) adds you to `watchers` and removes you from `unwatchers`;
       - someone else adding you in the picker adds you to `watchers` and removes you from `unwatchers` (a person can put you back on a thread you left; the next Unwatch leaves again);
       - nobody but you can put your id in `unwatchers`.
       Readers: `notify-item.ts` fans comments (`task_comment`, honouring the `comments` inbox toggle) and status changes (`status_changes` toggle) to `watchers` minus the actor, and never to anyone in `unwatchers`. Assignees are notified of assignment (`task_assigned`) whether or not they watch, because that is a different message. This is what makes the field real (settings §9.1 rule).

- **States**:
  - loading: after 200ms the rail logo pulses; the body shows skeletons at exact heights (title bar 60%, four 36px field rows 40/80/40/60, a 96px description block, a 36px row) and one 13/400 `--os-ink-2` value line under the first skeleton; no `Loader2`, no "Loading…" text.
  - empty: not applicable to a task; empty sections are hidden behind "Add to task"; Comments empty = one 15/400 `--os-ink-2` line "No comments yet"; Activity always has "created this task".
  - error (fetch failed): quiet four-dot row illustration, "Couldn't load this task", text link "Retry". Not found, deleted, or no role (the three are one state on purpose, so a 404 never confirms that a task exists): the same illustration, "This task was deleted or you no longer have access", and one `BackButton{fallbackHref="/home"}` labelled "Home" (or the `?returnTo=` destination when the URL carried one). One control. No blue "Go to Today" link: that line of `item/[id]/page.tsx:122` is deleted, not re-pointed (§0).
  - read-only: the Can view / Can comment rendering in §1, the one banner under the title row, lock cursor on values.
  - denied: the 404 above. There is no locked state for a task (§1 Access, case 2).
  - offline / session expired: the shell's 401 re-login prompt (shell unit). An in-flight autosave shows "Not saved, retrying" and keeps the draft. **Drafts survive the 12h session lapse**: this host subscribes to the shell's `workwrk:session-expired` event through `useDraftOnExpiry` (spec-shell §1.10 item 3 names the task drawer as one of the five editors that must) and flushes one payload to `localStorage["workwrk:draft:task:<itemId>"]` = `{ title?, description?, comment?, savedAt }` before the redirect. On the next mount with a stored payload the body shows one 36px strip above the title, `--os-warning-bg`, 13/400: "You have unsaved changes from {relative time}" with two text links **Restore** (re-fills exactly the fields present in the payload and clears the key) and **Discard** (clears the key). The strip never auto-applies, so a restore can never overwrite a newer value someone else saved. The key is cleared on a successful save of that field and on Discard, and is namespaced per task so two open tasks never collide. The same payload and the same strip serve the drawer, the page and the panel.
  - archived: a slim `--os-warning-bg` banner "Archived · Restore" under the title row (Restore for Can edit and above, `POST /api/items/[id]/restore`); everything else read-only for everyone but Full access (access rule 12).

### `/item/[id]?comment=<updateId>` (same page file; also `?comment=` on the drawer intercept)

- **Purpose**: land on the exact comment someone told you about.
- **Who sees it**: whoever can see the task (§1 Access); the parameter changes nothing about access, because a comment is never readable by anyone who cannot read the task.
- **Entry points**: the Inbox rows for `mention` and `task_comment` (both link `/item/<id>?comment=<updateId>`), the bell popover's comment rows, "Copy link to comment" in a comment's "…", a Talk message quoting a comment, an email notification.
- **Top bar / Secondary sidebar / Page header stack / Body layout**: exactly the page block above (or the drawer block, when the link is followed by a soft navigation from a list). The only difference is what happens after first paint.
- **Behaviour on arrival**: the body opens on the **Comments** tab whatever the last tab was; `CommentThread` receives `deepLinkId`; once the thread has rendered, the referenced comment scrolls into view with 96px of headroom (`scrollIntoView({ block: "center" })` when the thread is shorter than the viewport) and pulses once: its row background goes to `--os-brand-soft` and fades to transparent over 1200ms `--os-ease-out`, one time, no border, no outline, nothing that stays. Focus moves to the comment row so a screen reader reads it and so `Tab` continues from there. The `?comment=` parameter is then stripped with `router.replace` so a refresh does not pulse again and Copy link copies the clean task URL.
- **Paging**: the thread loads oldest first in pages of 50. When `deepLinkId` is set, the first request is `GET /api/items/[id]/updates?around=<updateId>` instead of the plain first page: the server returns the page containing that comment plus the 25 before it, with cursors in both directions, so a comment 400 replies deep is on screen immediately and "Load earlier" and "Load newer" rows sit above and below. This is the one reason `around=` exists.
- **States** (the failure paths `CommentThread.deepLinkId` needs, in the order they are checked):
  - **the comment was deleted**, or the id is not on this task: the task renders normally on the Comments tab, nothing pulses, and one 13/400 `--os-ink-2` line sits above the thread for 8 seconds: "That comment was deleted." No toast, no error colour, no retry. A deleted comment leaves no placeholder in the list, so there is nothing to scroll to.
  - **the referenced comment exists but the thread failed to load**: the thread's own error row ("Couldn't load comments · Retry") with the same quiet line above it, "Opening a comment. Retry to see it."; the retry re-issues the `around=` request, not the plain first page.
  - **the viewer has Can view on the task**: the deep link works exactly the same. Reading a comment needs Can view, not Can comment; only the composer and the reactions are gated. There is no partial-read case on a task: a viewer who can read the task can read every comment on it, because comments carry no grants of their own (access §3.2). A task the viewer cannot read is the 404 of §1, reached before any of this.
  - **the task is archived**: unchanged, read-only, with the Archived banner; the deep link still lands.
  - loading, empty, error, read-only, denied, offline / session expired: as the page block.
- **Keyboard**: as the page. Nothing new.
- **Data**: `GET /api/items/[id]/updates?around=<updateId>` (new parameter on the existing route; returns `{ updates[], cursorBefore, cursorAfter }` and 200 with an empty `updates` plus `{ missing: true }` when the id is not found, never a 404, so the task still renders).
- **Realtime**: as the page.
- **What changes vs today**: `?comment=` does not exist today, so a comment notification drops you at the top of a thread and you hunt. The deep link, the `around=` page and the one-time pulse are all new.
- **Open questions**: none.

1. **API contract first, additive.** `GET /api/items/[id]` gains `decision`, `breadcrumb`, `watcherIds`, `parent`; `PATCH /api/items/[id]` gains `boardId` (move: re-parents the row, remaps `status` to the target List's status with the same group else its first Active status, keeps `position` at the end, writes `MOVED` activity on both Lists, requires Can edit on both) and `watcherIds`;
