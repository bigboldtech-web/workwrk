Object-level rules used by this unit, verbatim from access §3.3 and §9: Goal owner = Full access; Contributors (USER, TEAM, DEPARTMENT, ROLE, TAG grants on `{ type: "goal" }`) = Can edit, which means check in and comment, never rename, delete, share or transfer; manager chain over the owner = Can edit on the owner's goals, plus the right to create goals for that person and to assign an owner within their chain; People team = the same over everyone; Owner/Admin = Full access. `okrs.delete` = owner or Owner/Admin. `kras.assign` and `kras.recordKpi` for a manager = Can edit on the target person. Agents keep everything a Member has here except Delete goal and Export (there is no export on these routes today, so nothing renders).

Denial is the one convention (access §5.5): not signed in → `/login?callbackUrl=`; not discoverable → 404 inside the shell; has a role but not the action → the control is not rendered; if reached anyway the API 403s and the client toasts "You need Can edit for that. Ask {owner}." with Request access. The four legacy bounces (`/people/me`, `/today`, `/team/alignment`, `/dashboard`) are deleted from every page in this unit.

**Which denial shape, in three situations** (the cross-unit resolution; all three are correct, and each names one situation, so nobody applies the wrong one):

1. **An app key the viewer's rule excludes** (`goals`, `kra-kpi`, `alignment`, `kpi-reviews`, `rollup`): the in-shell 404 with no sidebar row. There is no object here, so there is nobody to request from (access §5.5 rule 6). This is the shape every route in this unit uses.
2. **A view of a page the viewer already holds** (`/okrs?view=team` for a Member with no reports, `/kra-kpi?view=orphans` for a plain Member): never a denial. The page renders its default view, `router.replace` strips the parameter, and one 13/400 `--os-ink-2` notice line sits under the views row (access §5.5 rule 4). The pill itself does not render for that viewer, so the case only arises on a pasted or stale link.
3. **An object the viewer can discover but holds no role on**: `LockedPage` with Request access (rule 3). No goal is ever discoverable, so this shape never renders in this unit: a goal the viewer holds nothing on is the 404 of §1 above, and the read-only banner's Request is the only request path into a goal.

`<AppOff>` is only for an app the org hid or floored in the Apps config; `<ModuleOff>` only for a premium module switched off. Neither stands in for a role denial. The one sanctioned exception to situation 1 anywhere in the product is `spec-teams-people`'s two app-key `LockedPage`s on `/team` and `/team/workload` (it supplies those `APP_RULES` rows itself and writes them with an explanatory sentence and no Request access, flagged to the access unit, with the in-shell 404 as the fallback if declined). This unit's four Teams-hub pages take the 404, not that exception.

**Can a goal be requested?** Yes, but only from inside the goal, never from outside it. A goal is never discoverable (access §5.3 "role none, not discoverable"): someone with no role on it gets a 404, no search row, no locked page, so there is nothing to request from. A viewer who is already on the page (Can view, which for goals means the owner shared it or the goal is Company level) already knows the goal exists, so asking its owner for Can edit leaks nothing: the read-only banner's **Request** and the 403 toast's **Request access** both open the §5.6 flow (`POST /api/access-requests` at Can edit; the Inbox row goes to the goal's Full holders, which for a goal is the owner, then Admins). Toggle 3 (findable) does not gate this, because it gates discoverability and goals have none. If the founder prefers no request path at all, the fallback is one line: drop Request from the banner and from the toast and leave "Ask {owner}" as plain copy; nothing else in this unit changes.
