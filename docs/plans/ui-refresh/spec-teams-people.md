### Access

Vocabulary is the access model's only: org roles Owner / Admin / Member / Guest, the Agent flag, the People team, the manager chain (solid or dotted, any depth, `hasReports`), object roles Full access / Can edit / Can comment / Can view, and `can(viewer, action, ref)` with the refs `{ type: "person_card" }`, `{ type: "person" }`, `{ type: "app", key }`, `{ type: "org", action }`. Every page calls `gatePage()` in its server component, wraps its body in `<AccessProvider>` and renders from `useAccess()`; every API named in §2 calls `requireCan()` or `accessibleIds()`. `requireManagerPage`, `resolveAccess({ type: "module" })`, `MANAGER_LEVELS`, `ORG_WIDE_ALIGNMENT_LEVELS`, `DIRECTOR_LEVELS`, `useRole()`, `checkPermission("organization", "manageDepartments")` and `isManager()` disappear from every file in this unit (access step 1 wrappers first, direct calls by step 6).

**The Guest rule for this hub, in one place.** A Guest never sees the Teams hub (access §2.3: "Planner, Teams and AI are never shown to a Guest"), so no route in this unit renders for a Guest and every one of them is the shell 404, the "role none, not discoverable" shape of access §5.3. A Guest still has everything access §2.3 promises them, just not here: their own record is **My settings › Profile** (`/account/profile`), where they view their card and edit name, avatar, phone, password and MFA, and the avatar menu's "My profile" row already points a Guest there rather than at `/people/me` (spec-shell §2.12, which settles this route's Guest case; this unit does not invent a shell fallback). A Guest's view of a Member is the directory **card** that `person_card` VIEW gives them inside pickers, @mentions and the Talk profile popover (access §11 invariant 3: "Guests never see the directory. `person_card` VIEW for a Guest is true only for users in `accessibleUsers()` of an object the Guest holds"), and those surfaces belong to the shell and Talk units, not to `/people/[id]`. Nothing a Guest can reach today stops being reachable.

**The three denial shapes, stated once so nobody applies the wrong one.** Six units reached three different answers for a manager-scoped or app-key-gated page, and all three are right because they are three different situations:

1. **An app key the viewer's rule excludes** is the **in-shell 404** with no sidebar row (access §5.5 rule 6: no object, so nobody to request from). In this unit that covers every `/people*` and `/organization` route for a Guest.
2. **A view of a page the viewer already holds** (`/planner?calendar=team`, `/timesheets?view=approvals`, and in this unit any `?view=` or `?tab=` the viewer cannot hold) renders the **default view**, strips the parameter with `router.replace` and shows one 13/400 notice line in `--os-ink-2` (rule 4). No 404, no lock screen: the page itself is theirs.
3. **An object the viewer can discover but holds no role on** gets **`LockedPage` with Request access** (rule 3). In this unit that is a person record outside the viewer's reach only where a `person` object role is the gate.

`/team` and `/team/workload` are the one sanctioned departure from shape 1, per §0: `LockedPage` with an explanatory sentence and no Request access, flagged to the access unit, with the in-shell 404 as the fallback if declined. Separately, and not denial shapes at all: `AppOff` is only for an app the org hid or floored in Settings › Apps, and `ModuleOff` only for a premium module switched off. Neither ever renders in this hub for a scope or role reason.

Read-only mode everywhere: a control the role cannot use is not rendered, never disabled (access §5.4). The only banner is the slim "View only" line on the Job title page for Members without the write right. No page in this unit redirects on denial; `/people/me`, `/today`, `/team/alignment` and `/dashboard` as bounce targets are deleted (access §5.5).

People-data field writes on the person record follow settings §9.2a exactly (self-service fields self and Admin; placement fields manager chain for their chain except `managerId`, People team and Admin; membership fields Owner and Admin in the Members drawer only). The person page never renders a control for a field the viewer cannot write.

### Presence dots (one rule for the whole unit)

The 8px presence dot on an avatar reads `User.presenceStatus` and `User.presenceUntil`, which are **new columns** created by the settings unit's one SQL file (settings §9.5, step S4, alongside `User.weeklyCapacityHours`). Settings §9.5 requires that "pages that need the three columns ship behind the migration; every reader tolerates a missing column", so:

- Every surface in this unit that draws a dot (Directory Person column, the person record title row, My team Person column, the Skills drawer holder rows, the Org chart rows) reads the field through one helper that returns `null` when the column or the value is absent, and **draws no dot at all** when it is null. No grey "unknown" dot, no placeholder: an absent value means the avatar renders alone, at the same size and position, so the row never reflows when the column lands.
- The dot is decorative on its own, so it always carries a tooltip with the words ("Active", "In a meeting until 3 pm") and never encodes anything a person cannot read as text.
- Until S4 ships, the helper returns null everywhere and the unit behaves exactly as it does today. T1 therefore depends on settings S4 for the dot and on nothing else (§4).
