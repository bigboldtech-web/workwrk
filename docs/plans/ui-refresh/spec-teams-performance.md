### PO-1 reconciled with the goals unit (one route, two entry points)

An earlier draft of this spec called `/team/reviews` "the one decision surface" and said the Alignment board "stops trying to approve inline". `spec-goals.md` §2 `/team/alignment` and its Sub-teams view keep an **Actions** column with a secondary **Approve** and a ghost **Request changes** on rows whose review is Submitted, plus a Request changes popover. Both specs cannot be right, so here is the settled version, agreed as the goals unit's, and this spec adopts it:

- **PO-1 was a wrong verb, not a second surface.** The bug the audit recorded is that the board `POST`ed to a route that only accepts `PATCH`, so every inline approval failed silently. The fix is the verb and the payload, not the button.
- **One route, one payload, one permission rule**: `PATCH /api/weekly-reviews/[id]/manager-review` with `{ decision: "APPROVED" | "CHANGES_REQUESTED" | "REOPEN", notes }`, gated by `requireCan("edit", { type: "person", id: subjectId })`. The goals unit's Actions column and this unit's drawer footer both call exactly that, so the decision can never be written two different ways.
- **Two entry points with different jobs.** The Alignment board is the **one-click** surface: a manager who already knows the week is fine approves from the row without leaving the board. `/team/reviews` is the **reading** surface: the whole review (KRA progress, KPI snapshots, highlights, blockers, plan) in a drawer, with the notes field, for the reviews that need reading. Neither is a duplicate of the other because neither renders the other's content.
- **They stay in sync**: a decision written from either place flips the same `WeeklyReview.managerDecision`, refreshes the same sidebar count, and writes the same Inbox row to the employee. `/team/reviews` re-fetches on focus and the board does the same, so a manager who approved on the board sees that row in **Acted** here.
- **What this spec gives up**: the phrase "the one decision surface" and the sentence "the Alignment board, which stops trying to approve inline". What the goals unit gives up: nothing; it keeps the column, and its Request changes popover uses the same required-notes rule this spec states for the drawer footer (a Request changes without a note is not sendable, in both places).

### One primary at a time

Design system §5.8's rule is one blue button per page, and this unit reads it as one blue button **on screen**, not one per layer. Three surfaces here open a drawer or modal that owns its own primary (the manager review drawer's **Submit manager review**, the weekly review drawer's **Approve**, the survey builder's **Publish**, every confirm's action button), and in every case:

- While a drawer or modal with a primary is open, the page's title-row primary is **not rendered**. It is removed, not greyed, so the read is unambiguous and the rule matches how every other control in this unit handles "you cannot use this right now" (access §5.4).
- The page primary returns on close, computed fresh from the same `can()` plus state table it was computed from before, so it can legitimately come back as a different action (a reviewer who just finished their last person gets no button rather than "Open next review").
- A confirm modal opened **from** a drawer is the one stacked case the design system forbids (§4.5 "no stacked modals"), so a destructive confirm inside a drawer renders as an inline confirm strip in the drawer footer instead: the question at 13/400, then Cancel and the danger action in place of the footer's usual pair.

`/team/reviews` already had the right answer for a different reason (it has nothing to create, so its title row carries no primary at all and only the drawer's Approve is ever blue). This rule is what makes `/reviews/[id]` behave the same way.

## 6. Open questions for the founder

Only the genuine ones, each with the answer this spec assumes so no build work blocks on it.

1. **Does the employee see their own 9-box placement?** Assumed **no**: the grid is manager and People team information, and a person's record shows their performance band and outcome, not their box.
2. **Is four the right floor for showing candor and anonymous survey results?** Assumed **four answers**, so a five person department cannot be de-anonymised by arithmetic.
3. **Are the nine box labels fixed or editable per org?** Assumed **fixed**, with the long description always visible ("High performance, high potential") so nobody has to learn the word.
4. **Can a manager run a review cycle for their own chain, or is starting a cycle always a People team and Admin act?** Assumed **a manager may run one for their chain** (the cycle carries an audience), because a 20 person firm has no People team and the founder's rule is that a small company never opens Settings.
5. **Should peer feedback be visible to the subject after the cycle completes?** Assumed **the aggregate rating yes, the written answers no**, which is what keeps people honest in a small company.

**Not an open question, decided and cited**: who reads an anonymous survey's results. An earlier draft raised it here; access §3.3 already answers it ("Survey ... results = creator, Admin, People team"), so this spec cites that rule rather than re-asking it, and `/surveys` and `/surveys/[id]` are written to it. The same goes for the three other places this unit could have re-litigated a decided doc: the `/talent` URL is a hard constraint in access §3.5, the `LockedPage` shape is access §5.3, and the header stack is design system §4.4.
