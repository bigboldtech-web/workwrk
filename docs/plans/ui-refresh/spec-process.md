### Where a person searches (every list route)

There is one search per list route and it is the design system's `FilterPanel` search input (§5.2: 272px panel, heading "Filter {objects} by", a 36px search field above the checkbox rows), matching the programme convention that quick search moves into the Filter panel. Rules, identical on `/sops`, `/sops/my-sops`, `/sops/compliance`, `/process-runs`, `/policies`, `/policies/compliance`, `/policies/[id]/compliance` and `/agreements`:

- Typing writes `?q=` to the URL (debounced 300ms) so a search is linkable, survives reload and reopens the panel with the term in it.
- With a term set, the toolbar **Filter** chip turns `--os-surface-2` and reads "Filter · N" counting the term as one, so search is visible from the closed state; the panel header shows the term as a removable `Chip`.
- `/` (when no input is focused) and `⌘F` open the Filter panel with the search field focused, from anywhere on the page. Esc clears focus, a second Esc closes the panel; the term stays until it is cleared or "Clear all" is used.
- Per-route scope (what the term matches) is named in each route's Data block, and it is always server-side through the route's `q=` parameter, never a client filter over a truncated page.

Nothing in this unit renders a second search box: the top bar's centre field is the global search (design-system §4.3) and the sidebar field is the docs unit's tree filter.

Action rules that the pages render from (not enforce; the API enforces at the named route), in the access spec's own vocabulary:

- `publish` = Can edit on the SOP or policy, or, under toggle 7 = "Admins and People team only", Owner / Admin / People team (`PATCH /api/sops/[id]` status, `PATCH /api/policies/[id]` status).
- `delete` on a **SOP** = Full access on the SOP's folder, or the author on their own draft (`DELETE /api/sops/[id]`). Toggle 8 is **not** read here: access §8 scopes it to "Spaces, Folders, Lists, Docs, Tables", that is containers, and items follow their container's rule. The one place this unit reads toggle 8 is `delete` on a **SOP folder** (`DELETE /api/sop-folders/[id]`), which is a container. Policies and contracts: Owner and Admin only. A **run** is not a container either: `delete` on a run = Owner or Admin (`DELETE /api/process-runs/[id]`).
- Assigning a SOP or a policy to a person is `can("edit", { type: "person", id })` (access rule 9: self, manager chain, People team; FULL = Admin) at `POST /api/sop-assignments` and `POST /api/policies/[id]/assignments`. There is no `assign` action; the word "Assign…" is the button label, not a gate name.
- `export` (ledger CSV, compliance CSV) = `export`, never Guests, Agents or acting-as principals; contract `send` = Full access (`POST /api/agreements/[id]/send`).
- Agents: no Delete, no Export, no Full access (a folder share select clamps at Can edit), everything else as a Member.
- **One new `OrgAction`, flagged to the access spec**: `manage_process` on `{ type: "org", action: "manage_process" }`, rule = Owner, Admin, People team, never Guests, never Agents. It gates the three org-wide process taxonomies and their defaults: creating a top-level SOP folder, writing the policy-category and contract-folder lists, and writing the acknowledgement defaults (`PATCH /api/settings { section: "process" }`). It is an `OrgAction` in the `{ type: "org"; action }` union (which already ends open with "…"), not a member of the `Action` union, and it needs one `ENFORCED_AT` row (`enforcement.ts`: `manage_process → POST /api/sop-folders (top level), PATCH /api/settings {section:"process"}`) plus one golden case in `resolve.test.ts`. Everything else inside `/sops/manage` uses existing actions: `manage` and `create_child` on `{ type: "sop_folder" }`, `share` on `{ type: "sop_folder" }`, `delete` on `{ type: "sop_folder" }` under toggle 8.

Denial is the one convention (access §5.5): not signed in → `/login?callbackUrl`; not discoverable → 404 inside the shell; discoverable without a role → `LockedPage` at the same URL with one primary "Request access"; module or app off → `ModuleOff` / `AppOff`; role without the action → the control is not rendered, and a stale-tab API call shows the 403 toast "You need Can edit for that. Ask {owner}."

**Three denial shapes, three different situations** (cross-unit resolution, restated here so nobody applies the wrong one; six units had each reached a different single answer):

1. **An app key the viewer's rule excludes** → the **in-shell 404** with no sidebar row (access §5.5 rule 6: there is no object, so there is nobody to request from). In this unit that is `/agreements` and `/agreements?view=templates` for anyone outside Owner, Admin and the People team, and every route above for a Guest.
2. **A view of a page the viewer already holds** (the same shape as `/planner?calendar=team` and `/timesheets?view=approvals`) → the page renders its **default view**, strips the parameter with `router.replace`, and shows **one 13/400 `--os-ink-2` notice line** under the views row (access §5.5 rule 4). Never a 404, because the page itself is theirs. The instances in this unit are listed in "Views a viewer cannot hold" below.
3. **An object the viewer can discover but holds no role on** → `LockedPage` at the same URL with the one primary **Request access** (access §5.5 rule 3). This unit has **no instance of it**, because no object it owns is findable without a role (access §5.3: SOPs, SOP folders, policies, contracts and people data are never discoverable to someone with no role), so the precondition is never met here.

So this unit renders shapes 1 and 2 and nothing else. `LockedPage`, `AdminOnly` and every invented variant of them are not rendered by any route here. `AppOff` is only for an app the org hid or floored, and `ModuleOff` only for a premium module switched off; neither describes anything in this unit, so neither is rendered either. The teams-people unit's two app-key `LockedPage`s on `/team` and `/team/workload` are the single sanctioned exception to shape 1 across the product (it supplies those `APP_RULES` rows itself and writes them with an explanatory sentence and no Request access primary, flagged to the access unit, with the in-shell 404 as the fallback if declined); nothing in this unit copies that shape.

The upgrade path a read-only viewer does get is the §5.4 banner's **Request** link (View → Edit on the SOP's folder or the contract), which is the same `AccessRequest` flow, reached from a page they can already read. Nothing here redirects to `/dashboard`, `/today` or `/people/me`.

### Views a viewer cannot hold (shape 2, verbatim on every route)

The notice line is one sentence, 13/400 `--os-ink-2`, directly under the views row, no icon, no button, and it disappears on the next view click. The parameter is stripped with `router.replace` so a reload does not bring it back, and a bookmarked link still lands somewhere useful rather than on an error.

### Sharing an unfiled SOP (the default create path)

Create-on-first-change writes no folder, and Members always have create on unfoldered, so most new SOPs start with `folderId = null`. An unfiled SOP is a first-class object with its own grants, not a hole in the model:

- **Share always opens on something.** On `/sops/[id]` the Share button opens the one share dialog (access §6.1) on `{ type: "sop_folder", id }` when the SOP sits in a folder, and on `{ type: "sop", id }` when it does not. Both shapes are in the access spec's `ObjectRef` union, so this is one dialog with one object, not a second surface. The unfiled dialog shows the same rows: the "Everyone at {org}" row, the Restricted switch, named people at Full / Can edit / Can comment / Can view, and the "Public link" row (toggle 10).
- **Publishing an unfiled SOP is never silent.** The Publish confirm 400 names the consequence in the viewer's words: "Publish v{n}? Everyone at {org} will be able to read this SOP, because it isn't in a folder. Change who can see it in Share." with a "Share instead" text link beside Cancel. The EVERYONE VIEW grant is written by that action and is then visible and changeable as the dialog's "Everyone at {org}" row, so the widening has a control behind it.
- **Filing changes who can see it, and the picker says so.** Moving an unfiled SOP into a folder shows the line "This SOP will follow {Folder}'s sharing" under the folder picker; moving it out shows "Unfiled SOPs are read by everyone at {org} once published."
- **Folder delete says what it does.** The `/sops/manage` folder Delete confirm reads: "Delete {Folder}? The SOPs inside become Unfiled. Published ones will then be readable by everyone at {org} until you restrict them, and the folder's sharing is removed." with the count ("3 published, 1 draft"). The destructive primary is "Delete folder".
- A Guest never holds an unfiled SOP: the EVERYONE grant is Members only (access §2.3), so a Guest reaches a SOP only through an assignment or a named grant.

- `SOPFolderAccess` → `AccessGrant` (`SOP_FOLDER`, VIEWER / EDITOR / OWNER → VIEW / EDIT / FULL) is the access spec's step 4 item, not this unit's. Unfiled SOPs need no backfill: they carry no grants today and the EVERYONE VIEW grant is written on publish from then on, with the existing "published and unfiled" read rule covering everything published before.
- `SOP.category` / `subcategory` legacy columns stay mirrored and are never rendered.

What ships independently: steps 2, 4, 5, 6 and 8 need only the primitives. What is blocked: step 1 on the shell, access and docs-knowledge units; step 7's share dialog on access step 5; the public-link migration above on access step 3 (the `settings.access` schema must exist before anything writes to it).
